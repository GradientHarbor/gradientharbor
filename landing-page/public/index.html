How it works

The phone answers first. The cloud teaches.

Every request hits the router first. Confident ones stay on the device; the rest go to the teacher, whose answer goes back to the app and also becomes a training label. Each round, a new adapter ships to the phone, so fewer requests need the cloud.

  1. 1

    Route

    Student confidence (token logprobs) and output validators gate each request live on the phone. Out-of-distribution checks run asynchronously in the cloud.

  2. 2

    Escalate, redacted

    Hard requests go to the teacher right away, with names, IDs and amounts swapped for placeholders first.

  3. 3

    Learn off the request path

    Teacher answers and a 1% shadow sample become training data. Labeling and retraining never slow a reply.

  4. 4

    Ship a new adapter

    Each round, a LoRA-tuned student lands on the phone and the share of escalated requests falls.

One line

Wrap the agent you already have.

GradientHarbor sits around an OpenAI-compatible client in Python, or HarborKit in Swift on iOS. It captures messages, tool calls and outcomes, and every response tells you which model answered and why.

  • Nothing else in the app changes
  • The cloud keeps serving until the student is ready
  • Bring any teacher, including open-weight models
let agent = Harbor.wrap(student: .local("lfm3-1.7b-insurance"),
                        teacher: .cloud(teacherURL), task: "member-support")
let reply = try await agent.respond(to: message, tools: tools)
reply.route   // .student or .teacher, plus the gate that fired
from gradientharbor import wrap

client = wrap(OpenAI(), task="support-agent",
              teacher="<frontier-model>", student="lfm2-1.2b-support")
resp = client.chat.completions.create(model="auto", messages=msgs, tools=tools)
resp.harbor.route   # "student" | "teacher", plus the gate that fired

Focus

Built for the edge, not just cheaper in the cloud.

On-device inference

The student runs inside the app on an iPhone Air (A19 Pro, 12 GB) via MLX Swift, and keeps working in airplane mode.

Optimization

Distill into the smallest model that holds accuracy, drop reasoning tokens, shorten tool prompts, quantize to 4-bit and cache the fixed prompt prefix.

Data safety

Customer data stays on the device by default. What leaves is redacted first, limited to escalations and opt-in traces, and shown in a privacy ledger.

Data safety

Data leaves only when it has to, and you can see every time it does.

  • Local by default. Traces are encrypted at rest on the device. Nothing syncs without opt-in.
  • Redact before escalation. Names, member and policy IDs, birth dates, phone numbers and claim amounts become placeholders. The phone fills the real values back in locally.
  • Never-leave intents. A request that mentions a diagnosis or medication is answered on the phone or handed to a human, never sent to the cloud.
  • Train only on redacted traces. Any trace where the PII scanner still finds a match is rejected.
  • Fail closed. If the outgoing scan flags a request, it doesn't leave the phone.

Next

Where it goes after the hackathon.

Per-user adapters on the phone

Train a small LoRA on the device from that user's own traces, so personal data never leaves at all.

Android and NPU

Ship the student as LiteRT-LM for lower memory and multi-token prediction, and run the same file on Android. NPU export via LiteRT or ZETIC.

Trajectory distillation

Distill whole multi-step agent runs, evaluated by replaying against mock tools.

Race mode and outcome RL

Start student and teacher together on latency-critical paths, and move from SFT to RL once real reward signals exist.

As a company

One trace stream, compiled to every device.

The asset is the loop: redacted traces, evals and a router that knows when the student is wrong. Models become a compile target, and every build is checked by the same evals.

Next

Every runtime

Core ML and the Apple Neural Engine, LiteRT on Android, and NPUs via LiteRT or ZETIC, from the same traces.

Next

Built-in platform models

Apple stopped supporting custom Foundation Models adapters in OS 27, so for built-in models we compile the traces into prompts, tool definitions and output schemas, and train adapters wherever a platform allows them.

Then

Smaller models per app

Pruning, vocabulary trimming and quantization-aware distillation, tuned for each app's download size and battery budget.

Later

New architectures per use case

Search model shapes (depth, width, attention, vocabulary) per use case against the same evals. Research-heavy, and the furthest out.
